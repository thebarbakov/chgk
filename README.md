# CHGK

CHGK — full-stack приложение для проведения игры в формате «Что? Где? Когда?». Я делал его как рабочий инструмент для офлайн/онлайн-игры: администратор готовит контент и составы, ведущий управляет ходом игры, игроки отправляют ответы, а отдельный TV-экран показывает состояние для зала.

Проект закрывает типовые задачи небольшой игровой платформы: подготовку пакета вопросов, сбор команд по PIN-коду, синхронизацию нескольких интерфейсов в реальном времени, работу с медиа и фиксацию результатов.

## Что реализовано

- **Админка для подготовки игры.** Есть авторизация администратора, CRUD для блоков вопросов, серий, вопросов, игр, команд и игроков. Вопросы можно объединять в блоки, привязывать к играм и раскладывать по секторам.
- **Поддержка разных типов вопросов.** В модели и интерфейсах учтены обычные вопросы, блиц и суперблиц. Для серий хранится порядок вопросов, а на поле серия попадает как один сектор.
- **Пульт ведущего.** Ведущий подключается к активной игре, запускает интро, показывает правила/информацию/поле, вращает волчок, открывает вопросы, управляет таймером, медиа, черным ящиком, ответами и очками.
- **Интерфейс игрока.** Игрок выбирает активную игру и команду, подключается по PIN-коду и отправляет ответ во время обсуждения. Команда блокируется на время подключения, чтобы один слот не заняли несколько участников.
- **TV-экран для зала.** Отдельная страница для проектора показывает интро, игровое поле, выбранный сектор, вопрос, таймер, медиа, ответы, счет и финальный экран.
- **Realtime-синхронизация.** Состояние игры синхронизируется через WebSocket: вращение, выбранный сектор, раскрытие вопроса, таймеры, отправленные ответы, обновление счета и завершение игры.
- **HTTP API для администрирования и публичных сценариев.** Бэкенд отдает активные игры, статусы команд, сектора, результаты и административные CRUD-эндпоинты.
- **Загрузка медиа.** Через админский API можно загружать файлы для интро, вопросов, ответов и звуковых эффектов. Для папок заданы ограничения по MIME-типам и размеру файла.
- **PostgreSQL-схема.** В проекте описаны таблицы для игр, блоков вопросов, серий, вопросов, команд, игроков, секторов, ответов и очков.
- **Production-настройки.** Есть конфигурация через env-переменные, CORS с allow-list, cookie-сессия администратора, rate limiting для чувствительных сценариев и чеклист деплоя через reverse proxy.

## Технологии

### Frontend

- Next.js 16 с App Router
- React 19
- TypeScript
- Tailwind CSS 4
- Fetch API и WebSocket для связи с бэкендом

### Backend

- Node.js
- Express
- TypeScript
- `ws` для WebSocket-сервера
- Zod для валидации входных данных
- Multer для загрузки файлов
- Cookie-based авторизация администратора на HMAC-токенах

### Database

- PostgreSQL
- `pg`
- SQL-схема в `back/utils/db/gen_tables.sql`

### Infrastructure

- Отдельные приложения `front/` и `back/`
- Раздача загруженных файлов из backend-приложения через `/uploads`
- Reverse proxy для маршрутизации `/api/*`, `/ws`, `/uploads/*` и frontend-страниц

### DevOps / CI

- Скрипты сборки и запуска через npm
- Production checklist в `DEPLOYMENT.md`
- Отдельной CI-конфигурации в репозитории нет

### Integrations

Внешних продуктовых интеграций в коде нет. Основная интеграция внутри проекта — связь frontend-клиентов с backend API, WebSocket-сервером и PostgreSQL.

## Архитектура

Проект разделен на две части:

```text
chgk/
├── back/                         # Express API, WebSocket и работа с PostgreSQL
│   ├── src/server.ts             # HTTP routes, WebSocket-события, загрузка медиа
│   ├── src/db.ts                 # Репозитории для таблиц PostgreSQL
│   ├── src/store.ts              # Runtime-состояние активной игры в памяти
│   ├── src/adminAuth.ts          # Сессии администратора
│   ├── src/config.ts             # Env-конфигурация backend-приложения
│   ├── Chgk/                     # Доменные сущности и API-контракт
│   └── utils/db/gen_tables.sql   # SQL-схема базы данных
├── front/                        # Next.js-приложение
│   └── app/
│       ├── admin/page.tsx        # Админ-панель
│       ├── host/page.tsx         # Пульт ведущего
│       ├── player/page.tsx       # Интерфейс игрока
│       ├── tv/page.tsx           # Экран для зала
│       ├── lib/api.ts            # Клиент HTTP API и WS-конфигурация
│       └── components/ui.tsx     # Общие UI-компоненты
├── DEPLOYMENT.md                 # Чеклист production-деплоя
└── README.md
```

### Backend

`server.ts` содержит HTTP API и WebSocket-обработчики. Административные маршруты подключены под `/api/admin`, публичные сценарии — под `/api/games/*`, `/api/teams` и `/health`. Для realtime используется один WebSocket endpoint `/ws`.

Работа с базой вынесена в репозитории в `src/db.ts`: каждый репозиторий отвечает за свою область — игры, блоки вопросов, серии, вопросы, команды, игроки, сектора, ответы и очки. SQL-схема лежит отдельно, без ORM, поэтому структура данных хорошо видна и не спрятана за миграционным фреймворком.

Часть состояния игры хранится в памяти процесса в `src/store.ts`: подключения, блокировки команд, текущий сектор, таймер, выбранный вопрос и runtime-статусы. Постоянные данные — вопросы, игры, команды, ответы и результаты — хранятся в PostgreSQL.

### Frontend

Frontend построен на Next.js App Router. Для каждой роли сделана отдельная страница:

- `/admin` — подготовка контента и игр;
- `/host` — управление ходом игры;
- `/player` — подключение команды и отправка ответа;
- `/tv` — полноэкранный вывод для зала;
- `/` — стартовая страница с выбором роли.

Клиентская работа с backend API собрана в `front/app/lib/api.ts`: там задаются базовые URL, формируется WebSocket URL, обрабатываются JSON-запросы, FormData-загрузка и ошибки API.

### Поток игры

1. Администратор создает блоки вопросов, команды, игроков и игру с PIN-кодом.
2. К игре привязываются блоки вопросов, после чего backend генерирует сектора.
3. Ведущий, TV-экран и игроки подключаются к активной игре.
4. Ведущий управляет экраном, волчком, вопросами, таймерами и начислением очков.
5. Игроки отправляют ответы, backend сохраняет ответы и рассылает события всем подключенным клиентам.
6. После завершения игры backend считает результаты и отправляет финальное состояние на TV-экран и пульт ведущего.

## Как запустить проект

### Требования

- Node.js 20+
- npm
- PostgreSQL 14+

### 1. Подготовить базу данных

Создайте PostgreSQL-базу и примените SQL-схему:

```bash
cd back
psql "$DATABASE_URL" -f utils/db/gen_tables.sql
```

`DATABASE_URL` должен указывать на вашу базу, например:

```text
postgres://user:password@localhost:5432/chgk
```

Если в пароле есть спецсимволы вроде `&` или `%`, их нужно URL-encode-ить или заключить весь `DATABASE_URL` в кавычки при передаче через shell.

### 2. Настроить backend-переменные окружения

В `back/.env`:

```env
PORT=4000
DATABASE_URL=postgres://user:password@localhost:5432/chgk
ADMIN_LOGIN=admin
ADMIN_PASSWORD=change-me
APP_SECRET=change-me-too
CORS_ORIGIN=http://localhost:3000
```

### 3. Установить и запустить backend

```bash
cd back
npm install
npm run dev
```

Backend по умолчанию стартует на `http://localhost:4000`.

### 4. Настроить frontend-переменные окружения

В `front/.env.local`:

```env
NEXT_PUBLIC_API_BASE=http://localhost:4000
NEXT_PUBLIC_MEDIA_BASE=http://localhost:4000
```

Если переменные не заданы, frontend использует `http://localhost:4000` как fallback для API и WebSocket.

### 5. Установить и запустить frontend

В отдельном терминале:

```bash
cd front
npm install
npm run dev
```

Frontend будет доступен на `http://localhost:3000`.

### Production build

Backend:

```bash
cd back
npm run build
npm start
```

Frontend:

```bash
cd front
npm run build
npm start
```

### Тесты

Автоматических тестов в репозитории сейчас нет. Из проверок доступны TypeScript/Next.js сборки и frontend lint:

```bash
cd back
npm run build
```

```bash
cd front
npm run build
npm run lint
```

## Конфигурация

### Backend

Основные переменные backend-приложения:

| Переменная | Назначение |
| --- | --- |
| `PORT` | Порт Express-сервера. По умолчанию `4000`. |
| `DATABASE_URL` | Обязательная строка подключения к PostgreSQL. |
| `ADMIN_LOGIN` | Логин администратора. |
| `ADMIN_PASSWORD` | Пароль администратора. |

| `ADMIN_COOKIE_NAME` | Имя cookie с admin-токеном. По умолчанию `chgk_admin_token`. |

| Переменная | Назначение |
| --- | --- |

## Что было важно в разработке

- **Разделить роли без дублирования backend-логики.** Администратор, ведущий, игрок и TV-экран работают с одной игрой, но получают разные интерфейсы и разные действия.
- **Синхронизировать несколько экранов в реальном времени.** Ведущий управляет состоянием, а остальные клиенты получают события WebSocket и обновляют UI без ручного обновления страницы.
- **Сохранить постоянные данные отдельно от runtime-состояния.** Контент, игры, команды, ответы и очки лежат в PostgreSQL, а текущий процесс игры — в in-memory store. Для такого формата это простой и понятный компромисс.
- **Учесть специфику формата ЧГК.** В коде отдельно обработаны блиц, суперблиц, черный ящик, таймеры на разные длительности, закрытие сыгранных секторов и подсчет очков.
- **Сделать загрузку медиа управляемой.** Файлы разделены по назначению, а backend проверяет типы и размер, чтобы админка не принимала произвольные загрузки.
- **Подготовить проект к реальному запуску.** Конфигурация вынесена в env, CORS настраивается списком origin, admin-сессии подписываются HMAC, а в `DEPLOYMENT.md` описан базовый сценарий production-деплоя.

## Возможные улучшения

- Добавить миграции вместо одного SQL-файла схемы, чтобы проще развивать базу без ручного применения изменений.
- Покрыть ключевые сценарии тестами: генерацию секторов, начисление очков, WebSocket-события и admin CRUD.
- Вынести runtime-состояние из памяти процесса в Redis или другой shared storage, если понадобится несколько backend-инстансов.
- Настроить полноценный backend lint и CI-пайплайн для сборки frontend/backend перед merge или deploy.
- Улучшить обработку ошибок на frontend: единый слой уведомлений, состояния загрузки и повторные подключения для всех ролей.
- Добавить seed-данные или dev-скрипт, чтобы быстрее поднимать локальную демо-игру.
